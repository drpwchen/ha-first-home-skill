# 判斷原則

出處：作者家裡一套 Home Assistant 四年多的長期運作紀錄（243 條自動化、約 170 台裝置；2026 年整理成一個
部落格系列）。這裡只留原則與「它長什麼樣子」，不放個人居家細節。這些原則不會因為換機型而過期，
**型號與價格請當下查**。

## §1 盯物理狀態的活得久，搬資訊的是消耗品

- 活了好幾年、每天還在跑的自動化，形狀都一樣：**盯一個人會忘記看的物理狀態**——濕度、有沒有人、
  門開沒開、功率掉了沒、地上有沒有水。除濕自動化從第一批一直長到 22 條，是全家最沒爭議的一組。
- 幫你搬資訊的（爬網頁通知、轉寄信件、把別人的資料搬進來）是消耗品：資訊來源一換，整批就沒有存在的理由。
  做的時候就知道它會被淘汰，別堆太多細節。
- 規劃時的用法：每件生活小事都要翻成「盯什麼物理狀態」。翻不出來的放「可等」。
- 「先用最笨的方法跑三個月，再決定要不要做感測器」：清單上很合理的 DIY 感測（床下重量、瓦斯桶秤重）
  三年都沒做，每一項都輸給一個手動設的時刻表。

## §2 失敗長什麼樣子（新手不知道要問的）

| 失敗型態 | 長什麼樣子 | 規劃時怎麼防 |
|---|---|---|
| **回報成功 ≠ 事情發生** | 喇叭廣播無聲 18 天，系統每次都回報成功；憑證續期連續失敗三個月 | 驗收「事情有沒有發生」的那條線，要繞過送指令的那條線；監控第一天就裝 |
| **失聯的裝置留著舊值** | Zigbee 水感測器沒電 285 天，儀表板一直顯示正常；動作感應器凍在「有人」十天，系統眼裡玄關 24 小時有人 | Zigbee2MQTT／ZHA 的 availability 第一天打開，讓失聯真的變成「不可用」 |
| **動作感應器（PIR）偵測的是「動」不是「在」** | 人坐著看書，燈熄了 | 人會坐著的空間（客廳、書房）用插電毫米波；PIR 只放走道、廁所、門口 |
| **照度感應器看得到自己開的燈** | 開燈後照度在 0 和兩千之間跳 | 照度只當「開」的門檻，不當「關」的條件 |
| **燈光自動化的失敗都在「關」** | 開燈一個訊號就夠，關燈要證明沒人 | 「關」的等待時間永遠比「開」長；不信任單一顆感應器說的「沒人」 |
| **裝置重新上線也算一次觸發** | 換完電池，狀態從「不可用」跳到「有人」，被當成有人進來 | 觸發寫 `from:`（官方 skill 也有這條，HA 裝好後交給它） |
| **自動化被關掉沒人開回來** | 一條自動化在雲端 API 出錯時停在半路，排在後面的「開回來」永遠沒跑 | 「這段時間不要跑」用條件，不用關掉自動化 |
| **會誤報的警報會把真的一起帶走** | 另一支腳本每次「成功」也寄失敗信，信箱變成雜訊，真的失敗信每個月都沒細看 | 通知只在狀態真的改變時發；新手第一期的通知越少越好 |

## §3 雲端、依賴與爆炸半徑

- **免費層是產品決策，不是承諾。** 一條靠 IFTTT 免費 webhook 的接力路徑，在免費層拿掉 webhook 那天整條死。
  免費層可以放在方便的地方，不能放在唯一的路上。問：它明天消失，我家有幾條自動化跟著死？
- **備援要跟主路徑獨立。** 共用同一個信箱、同一套過濾規則、同一個整合的備援，跟主路徑同一天壞，
  而且因為平常用不到，壞得更安靜（實例：躺了 52 天沒人知道）。
- **整合的爆炸半徑是它管的所有裝置。** 同一個雲端帳號下一台家電離線，同一個整合底下的其他家電一起變
  unavailable。評估時把「這台壞了我少什麼」換成「這個整合壞了我少什麼」。
- **本地優先是選購時決定的，不是事後補救。** 買回來才問能不能斷網，答案多半是拆機刷韌體（市電那端要找電工）。
  一台裝置正連著雲，不代表它靠雲運作——要看中樞是從哪條路跟它講話（本地整合 vs 雲端 API）。
- **雲端家電可以買，但只能當旁觀者。** 靠廠商 app 才接得進來的家電，不能當別的自動化的前提。
- **Matter 買得到「控制不經雲」，買不到「一輩子不碰網路」**：部分廠商要先註冊帳號才開 Matter；
  Thread 裝置需要邊界路由器；Matter 只有各家共通的功能。
- **HACS 第三方整合**：HA 官方不審查、不維護。接之前看 `iot_class`、issue 區搜「unavailable」、
  維護者回應速度；能用的版本就是資產，更新提示不要順手按。

## §4 第一天／第一週就該做的（比買哪台重要）

1. **備份**：主機是消耗品，設定才是資產。自動每日全備份、保留一週以上，並且有一份不在主機上。
2. **監控三層，第十台裝置之前裝好**：
   - 裝置有沒有活著：Zigbee 的 availability。
   - 設定有沒有腐化：改名、換裝置、刪整合之後，掃一次引用到但已消失的實體（例如 HACS 的 Watchman）。
   - 該發生的有沒有發生：心跳（dead-man switch），**接收器放在家以外**——HA 停電時連「我停電了」都發不出去。
     接收器可以是外部的定時打卡監控服務（HA 定期去「打卡」，太久沒打卡它就通知你），或放在別處的另一台機器。
     用免費層服務當心跳接收器可以：它是第二條路、不是唯一的路（§3）；但要每季故意停一次 HA 測它真的會叫，
     否則它壞掉時你不會知道。
   這是六件事裡唯一一件「晚裝的代價會隨時間累積」的；作者晚了兩年九個月。
3. **記錄要開**：recorder 不要排除 `automation`，出事才查得到誰關的；但要設保留天數，不然資料庫會長到吃滿 SD 卡。
4. **命名規則**：房間_用途，第一台就照規則命名；改名會悄悄弄壞引用它的地方。
5. **實體開關保留**：任何一盞燈、任何一個裝置，都要能在 HA 整個掛掉時用手操作。

## §5 主機、協定、語音、攝影機的決策

### 主機

| 情況 | 建議方向 | 理由 |
|---|---|---|
| 只要燈、感應器、插座；維護者不想碰系統 | 官方成品盒（例如 HA Green） | 官方定位是「最簡單的開始方式」；沒有內建 Zigbee，要另買接收器 |
| 想跑攝影機物件偵測、本地語音，或有 AI agent 協助 | x86 小主機（N100 等級） | Frigate 官方文件主路線是 Intel N100＋OpenVINO；本地語音轉文字（Whisper）與本地大型語言模型都吃運算，Voice PE 頁面建議至少 N100 等級。但 zh-TW 官方語言表截至 2026-10 只標雲端語音支援，本地 Whisper／Piper 未標（見下方「語音分兩層」） |
| 家裡已有 NAS 或閒置電腦，**而且維護者就住在這個家** | 先用現成的跑 HA OS（虛擬機）試一個月 | 最省錢；確定會玩下去再買專用機。維護者到不了現場（幫爸媽家做）就不要：舊硬體出事沒人處理 |
| 自己燒 SD 卡的 Raspberry Pi | **新手不建議** | SD 卡壽命、記憶體不夠（作者的 Pi 4 穩態只剩 85 MB 可用記憶體） |

成品盒在台灣買不買得到、價格、小主機現價：**當下查**。作者 2026 年的看法是「有 AI 協助安裝的話，N100 小主機比成品盒好用」，
但這只在使用者願意碰、或有人（或 AI agent）幫忙設定時成立。

### 無線協定

- **Zigbee**：買存量。溫濕度、門窗、按鈕、水浸、功率插座這類便宜、電池型、要一次買很多顆的。要一支接收器
  （協調器），官方文件建議：接 USB 延長線、遠離 USB 3 埠與 Wi-Fi 路由器。插電的 Zigbee 裝置會當中繼。
- **Matter（over Wi-Fi／Thread）**：買增量。新買的插電型裝置優先挑有 Matter 標誌的。Thread 需要邊界路由器
  （很多家庭已經有，例如某些智慧音箱或電視盒），HA 官方接收器多半是 Zigbee 與 Thread 二選一。
- **Wi-Fi（非 Matter）**：只買有 `local_*` 整合的；數量多了會塞爆路由器，便宜的電池感應器不要選 Wi-Fi。
- **藍牙**：距離短，HA 主機要有藍牙或另加藍牙代理（ESPHome）。
- ZHA（HA 內建）vs Zigbee2MQTT（獨立軟體）：裝置少、都是大牌 → ZHA 少一層；裝置多而雜（白牌涂鴉 Zigbee）→ Zigbee2MQTT。
  答案會隨版本變，不要當定論。

### 語音

- 先問「手機推播夠不夠」。多數生活小事推播就夠。
- 要用講的：最省事是把 HA 裡的設備**接回使用者已經有的語音生態**（iPhone 家庭用 HomeKit Bridge 接回 Siri／HomePod；
  Google 家庭用 Google 整合）。它們笨，但聽得懂中文指令，家人不用學新東西。
  成本不一樣：HomeKit Bridge 是本地的；Google 整合要嘛付 Home Assistant Cloud，要嘛自架對外 HTTPS 網址＋Google 開發者專案。
- HA 自己的語音（Voice PE 等）：分兩層看。**聽懂中文指令句**這層沒問題，zh-TW 意圖句庫覆蓋 95%（2026-10）。
  **把聲音轉成文字**這層，官方語言表（`OHF-Voice/intents` 的 `languages.yaml`）截至 2026-10 對 zh-TW
  只標 Home Assistant Cloud（付費雲端）為支援，本地 Whisper 與 Speech-to-Phrase 都標不支援——
  想要「中文＋完全本地」的語音，品質要自己實測、別預設可用。Voice PE 發表時官方喚醒詞只有英文（2024-12 外媒報導，買前重查）。
  ==這些會變，用之前重查那份 `languages.yaml`==；
  文字轉語音的本地 Piper 只有 zh-CN 聲音、沒有 zh-TW；只有「聽懂自由句子」交給大型語言模型才需要顯卡。**新手第一期不放本地語音**。

### 攝影機

- 只買**本地就能吐 RTSP 串流**的機種，不要純雲端機種；廠商的偵測事件通常鎖在它的 app 裡，偵測要自己做（Frigate）。
- 買前確認**影像編碼**（H.264／H.265）和**音訊編碼**，以及能不能接進你自己的主機或 NVR（有些 NVR 軟體不吃 H.265）。
- 隱私底線是「不上雲」時，攝影機就決定了主機要升級。新手第一期多半放「可等」。

## §6 「別買」的型態

這些是**型態**，不是品牌黑名單；同一個品牌可能有好有壞，逐台查。

| 型態 | 為什麼 |
|---|---|
| 純雲端攝影機（家裡網路上不開任何本地服務） | 畫面要繞地球一圈才進家門；廠商改方案你就斷了 |
| 靠免費層服務接力的自動化路徑 | 免費層是別人的產品決策 |
| 自己燒卡的 Raspberry Pi 當主機 | 見 §5 |
| 電池型 PIR 當「房間有沒有人」的判斷 | 沒電時凍在最後的值，不會通知；人坐著它說沒人 |
| 靠廠商 app 才接得進來的家電當關鍵節點 | 爆炸半徑大，雲端出事全有或全無 |
| 清單上的 DIY 夢（第一期） | 先用最笨的方法跑三個月 |
| 便宜的 Wi-Fi 電池感應器大量買 | 吃電、塞路由器，多半走雲 |
| 租屋時：要接零線的智慧開關、電箱電表 | 不能動線路，退租要恢復；市電接線要電工 |
| 型號不在支援清單上的 Zigbee 白牌 | 「相容 Zigbee 3.0」不等於 HA 認得；同名不同版很常見 |

## §7 數字與常數

- **每個推估出來的數字都要答得出「分母是什麼」**。電費預估在計費週期重置後的前幾分鐘，分母只有一分鐘，
  外推直接跳到最高級距——規則沒錯、算術沒錯，數字沒意義。分母太小寧可空著。
- **寫死的常數會過期**：台電電價級距 2026-04-01 調過價，寫死在公式裡的舊級距會安靜地每天錯一點。
  任何寫死的費率、門檻，要寫進「每年檢查一次」的清單。
- **台電智慧電表**：截至 2026-09，HA 沒有成熟的官方整合；社群方案要抓帳密或瀏覽器 token，會過期。
  要的若只是「本期用了多少」，台電 app 本身已有 15 分鐘粒度的查詢。做自動化前先問：這個數字收到後我會做什麼不同的事？
  新手想看用電：功率感測插座（逐台家電）比整屋電表實用。
